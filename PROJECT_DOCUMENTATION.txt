1. PROJECT OVERVIEW
================================================================================

Gestion-Fonds is a backend REST API built with ASP.NET Core (.NET 8) that manages
the "Fonds Social" (Social Fund) of a company. It handles the complete lifecycle
of employee loan requests (demandes de prêt), from submission to repayment.

The system manages:
  - Companies (Societes) and their employees (Agents)
  - Types of loans (TypeDePret) with eligibility rules
  - Loan requests (Demandes) with a full state machine
  - Supporting documents (PiecesJustificatives)
  - Committee meetings (SeancesComite) and decisions (Decisions)
  - Contracts (Contrats), guarantees (Garanties), and repayment schedules (Echeances)
  - Monthly salary deductions (RetenuesMensuelles)
  - Annual budgets (BudgetFonds)

The project uses Code-First Entity Framework Core 8 with SQL Server.

4. HOW TO RUN THE PROJECT
================================================================================

PREREQUISITES:
  - .NET 8 SDK installed
  - SQL Server available (e.g., (localdb)\MSSQLLocalDB or your SQL Express)

STEPS:
  1. Build the solution:
     dotnet build

  2. Create/update the database (from the Infrastructure project):
     dotnet ef migrations add InitialCreate --project FondsSocial.Infrastructure
     dotnet ef database update --project FondsSocial.Infrastructure

     (If migrations already exist, just run: dotnet ef database update)

  3. Run the API:
     dotnet run --project FondsSocial.API

  4. Open Swagger UI:
     http://localhost:5201/swagger   (HTTP)
     https://localhost:7201/swagger  (HTTPS)

CONNECTION STRING:
  - Default in appsettings.json:
    "Server=.;Database=FondsSocialDb;Trusted_Connection=True;MultipleActiveResultSets=true;TrustServerCertificate=True"
  - The DbContextFactory also supports an environment variable override:
    ConnectionStrings__DefaultConnection
  - Fallback: (localdb)\mssqllocaldb

KEY RELATIONSHIP NOTES:
  - 1:N = One-to-Many (e.g., one Agent has many Demandes)
  - 1:1 = One-to-One (e.g., one Decision has one Contrat)
  - N:N = Many-to-Many (implemented via ParticipationSeance join table)
  - Delete behaviors:
      * Restrict: cannot delete parent if children exist (Agent→Demande, etc.)
      * Cascade: deleting parent deletes children (Demande→Pieces, Contrat→Echeances)
  - Soft delete: all entities have IsDeleted flag; global query filter hides deleted rows
  - Audit fields: CreatedAt, UpdatedAt, CreatedBy, UpdatedBy on every entity

6. ALL ENTITIES EXPLAINED
================================================================================

1. Societe (Company)
   - Code (unique), RaisonSociale (legal name), ReferentielReglesGestion
   - Relations: has many Agents, has many BudgetFonds

2. Agent (Employee)
   - Matricule (unique), Nom, Prenom, CIN (unique), IdentifiantUnique (unique)
   - Grade, Fonction, Adresse, Telephone
   - DateTitularisation (hiring date — used for seniority check)
   - SituationFamiliale (enum), NombreEnfantsACharge
   - SalaireMensuel (monthly salary — used for debt ratio)
   - Relations: belongs to Societe, has many Demandes, has many RetenuesMensuelles

3. TypeDePret (Loan Type)
   - Code (unique), Libelle, Categorie (enum: Logement/Vehicule/Autre)
   - Plafond (max amount), DureeMaxMois (max duration), FranchiseMois (wait period)
   - ModeCalculFraisGestion (enum), TauxOuMontantFraisGestion, Actif
   - Relations: has many PieceJustificativeRequises, has many Demandes

4. PieceJustificativeRequise (Required Document)
   - TypeDePretId, LibellePiece (e.g., "CIN"), Obligatoire (bool)
   - Relations: belongs to TypeDePret

5. Demande (Loan Request)
   - NumeroDossier (unique, auto-generated: D-YYYYMMDD-GUID)
   - AgentId, TypeDePretId, DateDepot, MontantDemande
   - StatutCourant (enum — current state), ScorePriorite (priority score)
   - Relations: belongs to Agent, belongs to TypeDePret
   - has many HistoriqueStatutDemandes, PieceJustificatives, Decisions

6. HistoriqueStatutDemande (Status History)
   - DemandeId, Statut, DateChangement, Auteur, Commentaire
   - Relations: belongs to Demande

7. PieceJustificative (Supporting Document)
   - DemandeId, TypePiece, CheminFichier, DateDepot, StatutVerification (enum)
   - Relations: belongs to Demande

8. MembreComite (Committee Member)
   - Nom, Prenom, Fonction, Actif
   - Relations: has many ParticipationSeances

9. SeanceComite (Committee Meeting)
   - Date, ProcesVerbal, StatutVisaSignature (enum)
   - Relations: has many Participations, has many Decisions

10. ParticipationSeance (Meeting Participation)
    - SeanceComiteId, MembreComiteId, AVise (bool), DateVisa
    - UNIQUE: (SeanceComiteId, MembreComiteId) — one member per meeting
    - Relations: belongs to SeanceComite, belongs to MembreComite

11. Decision (Committee Decision)
    - DemandeId, SeanceComiteId, SensDecision (enum: Favorable/Defavorable/Ajourne)
    - MontantAccorde, DateNotification, DatePeremption
    - Relations: belongs to Demande, belongs to SeanceComite, has one Contrat

12. Contrat (Loan Contract)
    - DecisionId, DateSignature, MontantPrincipal, FraisGestion, MontantTotal
    - DureeMois, DatePremiereEcheance
    - Relations: belongs to Decision (1:1), has one Garantie (1:1)
    - has many Echeances, has many RetenuesMensuelles

13. Garantie (Guarantee)
    - ContratId, AssuranceVieSouscrite, DateAssuranceVie, ReferencePoliceAssurance
    - TraiteSigneeLegalisee, DateTraite
    - EngagementRemboursementSigne, DateEngagement
    - AutorisationRetenueSalaireSignee, DateAutorisationRetenue
    - Computed property: ToutesGarantiesReunies (all 4 guarantees present)
    - Relations: belongs to Contrat (1:1)

14. Echeance (Payment Installment)
    - ContratId, NumeroEcheance, Date, CapitalRestantDu, Mensualite
    - CapitalAmorti, FraisGestion, SoldeRestant, Statut (enum)
    - UNIQUE: (ContratId, NumeroEcheance)
    - Relations: belongs to Contrat

15. RetenueMensuelle (Monthly Salary Deduction)
    - Mois, AgentId, ContratId, MontantARetenir, MontantEffectivementRetenu
    - Statut (enum), ReferencePaie
    - UNIQUE: (ContratId, Mois)
    - Relations: belongs to Agent, belongs to Contrat

16. BudgetFonds (Fund Budget)
    - SocieteId, Exercice (year), Categorie (enum), Ressources, Emplois, Solde
    - UNIQUE: (SocieteId, Exercice, Categorie)
    - Relations: belongs to Societe

BaseEntity (common to all):
  - Id (int, PK), CreatedAt, UpdatedAt, CreatedBy, UpdatedBy, IsDeleted (soft delete)

9. BUSINESS RULES & ELIGIBILITY CHECKS
================================================================================

When creating a Demande (POST /api/Demande), the DemandeService runs these
eligibility checks IN ORDER. If any fails, it throws InvalidOperationException
(returned as HTTP 400 Bad Request):

1. AGENT MUST EXIST
   → "Agent introuvable"

2. TYPE DE PRET MUST EXIST
   → "Type de prêt introuvable"

3. SENIORITY CHECK (Ancienneté minimale)
   → Agent must have DateTitularisation set
   → DateDepot must be at least 1 year after DateTitularisation
   → "Ancienneté minimale d'un an non respectée"

4. LOAN AMOUNT CAP (Plafond)
   → MontantDemande must be ≤ TypeDePret.Plafond
   → "Montant demandé dépasse le plafond"

5. FRANCHISE CHECK (waiting period between same-type loans)
   → If the agent has a previous demande of the same type (not Rejetee/Caduque),
     the time between the two must be ≥ TypeDePret.FranchiseMois
   → "Franchise non respectée"

6. DEBT RATIO CHECK (Taux d'endettement ≤ 40%)  ← THE "40% FUNCTIONALITY"
   → Agent must have SalaireMensuel > 0
   → TypeDePret.DureeMaxMois must be > 0
   → Calculate:
       existingMonthlyDeductions = sum of RetenuesMensuelles (Retenue/Prevue)
       estimatedNewMonthlyPayment = MontantDemande / DureeMaxMois
       debtRatio = (existingMonthlyDeductions + estimatedNewMonthlyPayment) / SalaireMensuel
   → If debtRatio > 0.40 → "Taux d'endettement supérieur au plafond de 40%"

7. CUMULATIVE HOUSING CAP (Plafond cumulé logement)
   → Only for TypeDePret.Categorie == Logement
   → Sum of all Favorable decisions' MontantAccorde for housing loans
     + current MontantDemande must be ≤ 30,000 DT
   → "Plafond cumulé logement dépassé"

8. PRIORITY SCORE (ScorePriorite) — calculated on creation:
   → +4 points per full year of seniority
   → +4 points if married (Marie)
   → +4 points if divorced/widowed with children (garde d'enfants)
   → +2 points per dependent child

OTHER BUSINESS RULES:

9. CLOTURE DEPOT (Close Submission):
   → Only allowed when StatutCourant == Deposee
   → All required documents (Obligatoire=true) must be provided
   → No document can be NonConforme
   → On success: StatutCourant → Enregistree

10. STATUS TRANSITIONS (State Machine):
    → Only valid transitions are allowed (see section 13)

10. THE "40% FUNCTIONALITY" — TAUX D'ENDETTEMENT (Debt Ratio)
================================================================================

This is the rule that limits how much of an employee's salary can be committed
to loan repayments. The maximum allowed is 40% of the monthly salary.

THE FORMULA:
  debtRatio = (existingMonthlyDeductions + estimatedNewMonthlyPayment) / monthlySalary

  Where:
    existingMonthlyDeductions = sum of MontantARetenir from all RetenuesMensuelles
                                where Statut is Retenue(1) or Prevue(0)
                                for this agent
    estimatedNewMonthlyPayment = MontantDemande / TypeDePret.DureeMaxMois
    monthlySalary = Agent.SalaireMensuel

  If debtRatio > 0.40 → REJECTED with error:
    "Taux d'endettement (X%) supérieur au plafond de 40%."

WHY IT MATTERS:
  - This is a key eligibility rule that prevents employees from over-borrowing
  - It is the ONLY rule that uses the RetenuesMensuelles table
  - It is explicitly tested in the unit tests (see section 16)

       "nombreEnfantsACharge": 0,
       "salaireMensuel": 1000,
       "societeId": 1
     }
     → Note the agent ID (e.g., 1)

  2. Create a TypeDePret with a short duration:
     POST /api/TypeDePret
     {
       "code": "PRET_DEBT",
       "libelle": "Pret Test Dette",
       "categorie": 1,

       "dureeMaxMois": 12,

       "tauxOuMontantFraisGestion": 2,
       "actif": true
     }
     → Note the type ID (e.g., 1)

     POST /api/Demande
     {
       "agentId": 1,
       "typeDePretId": 1,
       "dateDepot": "2026-08-01T10:00:00",
       "montantDemande": 10000
     }
     → Estimated monthly = 10000/12 = 833.33
     → Debt ratio = 833.33/1000 = 83.3% > 40%
     → EXPECTED: HTTP 400 with error "Taux d'endettement ... supérieur au plafond de 40%"

  4. Now try a Demande that PASSES 40%:
     POST /api/Demande
     {
       "agentId": 1,
       "typeDePretId": 1,
       "dateDepot": "2026-08-01T10:00:00",
       "montantDemande": 3000

================================================================================
13. THE DEMANDE LIFECYCLE (State Machine)
================================================================================

The Demande goes through a state machine. Only these transitions are allowed:

  Deposee(0) ──────────────→ Enregistree(1)
  Deposee(0) ──────────────→ AEtude(3)
  Deposee(0) ──────────────→ Rejetee(10)

  Enregistree(1) ──────────→ AEtude(3)
  Enregistree(1) ──────────→ Rejetee(10)

  AEtude(3) ───────────────→ PVVise(4)
  AEtude(3) ───────────────→ Ajournee(9)
  AEtude(3) ───────────────→ Rejetee(10)

  PVVise(4) ───────────────→ Signee(5)
  PVVise(4) ───────────────→ Rejetee(10)

  Signee(5) ───────────────→ DecisionNotifiee(6)

  DecisionNotifiee(6) ─────→ RetenueProgrammee(7)
  DecisionNotifiee(6) ─────→ DecaisseeCloturee(8)

  NOTE: ConvocationEnvoyee(2) and Caduque(11) exist in the enum but are
  NOT currently part of the transition map in DemandeService.

  The CloturerDepotAsync method automatically moves Deposee(0) → Enregistree(1)
  when all documents are complete and compliant.

15. COMMON ERRORS & TROUBLESHOOTING
================================================================================

1. HTTP 400 ValidationProblemDetails
   → A required field is missing/invalid, or a navigation object was sent.
   → Only send the fields listed in the examples.

2. HTTP 500 "clé en double IX_Agent_Matricule / CIN / IdentifiantUnique"
   → Unique constraint violation. Change the unique values (matricule, CIN,
     identifiantUnique) for each test.

3. HTTP 500 "clé en double IX_Societe_Code / IX_TypeDePret_Code"
   → Same issue for Societe.Code or TypeDePret.Code. Change the code.

4. HTTP 500 "clé en double IX_BudgetFonds_..."
   → (SocieteId, Exercice, Categorie) must be unique.

5. HTTP 500 "clé en double IX_ParticipationSeance_Seance_Membre"
   → A member can only participate once per meeting.

6. HTTP 500 "clé en double IX_Echeance_Contrat_Numero"
   → Each contract can only have one echeance per number.

7. HTTP 500 "clé en double IX_Retenue_Contrat_Mois"
   → Each contract can only have one deduction per month.

8. DO NOT SEND these fields in request bodies:
   - id, createdAt, updatedAt, createdBy, updatedBy, isDeleted
   - navigation objects (societe, demande, contrat, seanceComite, etc.)
